StoreManagement · Payments

Go live, one step at a time

Set up the databases, Razorpay, the single StoreManagement API, and the Flutter app in order. Use test mode first, then switch the server and app to production.

Deploy one API

The StoreManagement API uses SubscriptionPlatform.Core as a class library. Deploy the StoreManagement API only. The separate SubscriptionPlatform API is needed only temporarily if you use it to create the application and plan IDs.

Steps in this guide

  1. Understand the payment options
  2. Prepare accounts and hosting
  3. Set up the databases
  4. Create the application and plan
  5. Configure API secrets
  6. Set up Razorpay test mode
  7. Build and deploy one API
  8. Configure and release Flutter
  9. Test the complete flow
  10. Switch to Razorpay Live Mode
1

Understand what each payment option does

  • Free trial: access starts for the trial duration configured on the plan. No Razorpay payment is made.
  • 3 months, 6 months, and 1 year: each is a one-time prepaid Razorpay order. Customers must purchase again after expiry.
These are not automatic renewals.The current code does not create Razorpay recurring mandates or automatically charge customers when a term ends. Do not promise auto-renewal until recurring billing, retries, cancellation, and reconciliation are implemented.
2

Prepare accounts and hosting

  • Complete Razorpay merchant onboarding and activate the account for live payments.
  • Prepare a production HTTPS domain for StoreManagement API. Razorpay needs public HTTPS access to the webhook endpoint.
  • Prepare MySQL 8 or a compatible MySQL service, reachable privately from the API host.
  • Use .NET 10 hosting, or publish a suitable self-contained/container deployment.
  • Keep separate staging and production databases, credentials, Razorpay keys, and webhook secrets.
3

Set up both databases

StoreManagement uses one database. The subscription library uses a separate database called SubscriptionDatabase. They can be schemas on the same private MySQL server.

StoreManagement database

For a new database, start with StoreManagement.Api/Scripts/schema.sql. That schema already includes several columns from older alteration scripts. Do not blindly run every old ALTER TABLE file on top of it; duplicate-column errors can result. Apply only tables/features missing from your chosen database version. For an existing database, back it up and have the database administrator compare it with the scripts before applying changes.

For a fresh StoreManagement database, the separate tables not created by the base schema include the customer-credit tables and refresh-token table. Apply create_customer_credit_invoices.sql and add_refresh_tokens.sql after the base schema. The other numbered/alter scripts are upgrades for older database versions; apply only when the relevant columns or changes are missing. Keep a record of every SQL file applied.

Subscription database

From the StoreManagementApi solution root, create the subscription tables by applying the initial migration:

mysql -u <migration-user> -p < ../SubscriptionPlatform.Api/Migrations/001_initial.sql

If the database already exists from the older initial schema, back it up and apply ../SubscriptionPlatform.Api/Migrations/002_fixed_term_prices.sql once. Do not apply migration 002 after the current migration 001, because the fixed-term columns are already present. The application does not apply SQL migrations automatically.

Database accessUse a privileged account for schema changes and separate restricted runtime users for the API. Do not expose MySQL directly to the internet.
4

Create the application and plan IDs

The StoreManagement API needs an application GUID and plan GUID. If they are not already created, use the standalone administrative host once in a trusted development/staging environment. Do not deploy it to serve customer payments.

  1. From the solution root, run ../SubscriptionPlatform.Api/SubscriptionPlatform.Api.csproj. Configure its subscription DB connection, a random Authentication__SigningKey (at least 32 bytes), and a strong Authentication__BootstrapAdminKey (at least 32 characters). Use test Razorpay credentials if needed.
  2. Call POST /api/v1/auth/token with { "adminKey": "<bootstrap-admin-key>" } to get an admin bearer token.
  3. Call POST /api/v1/admin/applications with the admin token and { "name": "StoreManagement" }.
  4. Save the returned application id and application_key securely. The key is only shown at creation.
  5. Get an application bearer token via POST /api/v1/auth/token with { "applicationKey": "<application-key>" }. Create the plan using POST /api/v1/plans.

Enter your approved prices in integer minor units. For INR, 10000 means ₹100.00. Set the 3-month, 6-month, and yearly prices, currency, and trial days (0–90). Copy the returned application ID and plan ID for Step 5.

Stop the administrative host after provisioning. Do not run it alongside StoreManagement API on the same database unless you intentionally coordinate both background maintenance workers. See the administrative API endpoint guide for request examples.

5

Configure StoreManagement API secrets

Put these values in the hosting provider's protected environment configuration or secret manager, not in committed settings files:

ConnectionStrings__DefaultConnection=<StoreManagement MySQL connection>
ConnectionStrings__SubscriptionDatabase=<SubscriptionDatabase MySQL connection>
SubscriptionPlatform__ApplicationId=<application GUID>
SubscriptionPlatform__PlanId=<plan GUID>
JwtSettings__SecretKey=<random secret, at least 32 bytes>
Razorpay__KeyId=<key ID for this environment>
Razorpay__KeySecret=<API key secret for this environment>
Razorpay__WebhookSecret=<webhook secret for this environment>

Keep the Store API's JWT issuer and audience consistent with its login configuration. Configure email, Cloudinary, and other settings if you use those features. Use TLS for database connections when supported.

Never put server secrets in Flutter.Database passwords, the JWT signing secret, Razorpay Key Secret, Webhook Secret, and application key must stay server-side. The public Razorpay Key ID is provided to Checkout with the server-created order.
6

Set up Razorpay Test Mode and webhook

  1. In Razorpay Test Mode, generate test API keys. Set the Key ID and Key Secret on the staging StoreManagement API.
  2. Create a Test Mode webhook with this URL:
    https://<staging-api-host>/api/subscription/webhook/razorpay
  3. Subscribe to payment.captured and payment.failed. Set a webhook secret and configure it as Razorpay__WebhookSecret. This secret is separate from the API Key Secret.
  4. Allow public HTTPS POST requests to this exact API route. It does not use a user JWT; the server validates Razorpay's webhook signature.
  5. Confirm that webhook events reach the staging StoreManagement API. Do not point them to the standalone administrative API.

Razorpay dashboard labels can change; check its current webhook setup documentation. Use separate webhook configuration for test and live modes.

7

Build and deploy one API

From the StoreManagementApi solution root:

dotnet restore StoreManagement.sln
dotnet build StoreManagement.sln --configuration Release
dotnet publish StoreManagement.Api/StoreManagement.Api.csproj --configuration Release --output ./publish

Deploy the contents of publish/ as the StoreManagement API. The project reference packages SubscriptionPlatform.Core into the API output; you do not deploy a second API for customer payments. Set the Step 5 secrets on the host, enable HTTPS, then confirm the API starts and connects to both databases.

Razorpay confirms successful fulfilment should depend on captured payment state. Review its current test and go-live guidance.

8

Configure and release the Flutter UI

The Flutter app already has the subscription screen and Razorpay Checkout flow. Point its API base URL at the deployed StoreManagement API, not SubscriptionPlatform. The URL must end in /api.

Release Android APK

cd ../StoreManagementApp
flutter pub get
flutter analyze
flutter build apk --release --dart-define=API_BASE_URL=https://<production-api-host>/api

Release iOS IPA

flutter build ipa --release --dart-define=API_BASE_URL=https://<production-api-host>/api

Replace the host with your real HTTPS domain. If the default API URL in the app points somewhere else, always provide this build define. Sign the release using your normal Android/iOS store credentials. Test the installed release build on a device. Never pass the Razorpay Key Secret or Webhook Secret using --dart-define.

The UI reads plan options and status from the API, starts checkout with a server-created Razorpay order, and sends the checkout result back for server verification. A success callback in the app alone must not be treated as proof of payment.

9

Test the whole flow in staging

Use a staging database, staging API, and Razorpay Test Mode. Use only the test payment methods listed in the Razorpay dashboard.

  • Sign in to Flutter and confirm the subscription screen shows the configured options and prices.
  • Start a free trial. Confirm that no payment checkout opens and the API reports trial access.
  • Complete a test payment for each paid term: 3 months, 6 months, and 1 year. Confirm access begins only after server verification.
  • Try a failed or cancelled checkout. Confirm it does not grant access and that retry works.
  • Confirm an authorized but uncaptured payment does not unlock the app.
  • Check webhook delivery and API logs. Confirm invalid signatures are rejected and duplicate events do not grant duplicate access.
  • Sign out, sign in again, and restart the app. Confirm the subscription status is loaded from the API.
  • Call a protected API feature without an active trial or paid term. Confirm the app shows the subscription UI.
  • Repeat on an installed Android/iOS release build using the staging HTTPS domain.
Do not go live until all relevant checks pass.A successful compile does not verify credentials, webhook delivery, merchant activation, or a live payment.
10

Switch to Razorpay Live Mode and release

  1. After staging sign-off and Razorpay account activation, generate API keys in Razorpay Live Mode.
  2. Create a separate Live Mode webhook at https://<production-api-host>/api/subscription/webhook/razorpay, subscribe to the same events, and obtain its live webhook secret.
  3. Set the live Key ID, Key Secret, and Webhook Secret in the production StoreManagement API secret manager. Verify the production DB connection, application GUID, and plan GUID.
  4. Deploy the Release output from Step 7. Check startup, database access, HTTPS, and webhook reachability.
  5. Build and release Flutter with API_BASE_URL=https://<production-api-host>/api. Never ship Test Mode credentials in the app.
  6. Monitor API errors, Razorpay payments, webhook delivery, and settlements. Keep a support and reconciliation process for delayed or disputed payments.

Use Razorpay's current Live Mode key and go-live instructions and security checklist; menu names and merchant activation requirements can vary by account.

Before you accept real payments

Confirm that one-time prepaid terms meet your business needs. The current implementation does not provide automatic renewals/mandates, renewal retries or dunning, refunds, or invoice/tax management. Razorpay account setup and a passing staging test are required in addition to a successful build.
