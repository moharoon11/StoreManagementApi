The short version

A paid subscription has two separate records

Subscription answers: “Does this customer have access, and until when?”

Payment answers: “Did this checkout attempt get paid, and which Razorpay order belongs to it?”

The payment becomes paid first. Only then does the subscription become active.

Important rule

The browser never grants access

The app callback is treated as a request for verification. The server checks the Razorpay signature, fetches the provider payment, compares order/amount/currency, and updates the database.

Razorpay webhooks provide a second, independent path for delayed or missed callbacks.

Payment lifecycle

Follow one paid purchase

1

Start request

The server creates a subscription with pending_payment, creates a local payment with order_pending, then commits both.

2

Create order

Razorpay receives the server-calculated amount. Its returned order ID is stored in payments.razorpay_order_id.

3

Checkout

The client opens Razorpay Checkout using the returned public key, order ID, amount, and currency.

4

Verify

The server verifies the signature, fetches the provider payment, and compares order ID, payment ID, amount, currency, and captured status.

5

Activate

In one database transaction, payment becomes paid, the subscription becomes active, dates are calculated, and an audit row is inserted.

6

Expire

The worker later changes expired access to expired. An abandoned pending order expires after 30 minutes.

Project-specific notes

Things this implementation does not do yet

  • Paid terms are fixed local periods; automatic Razorpay recurring renewals are not implemented.
  • Changing a plan updates the subscription immediately and does not calculate proration or charge a difference.
  • The Store API derives the customer from the authenticated user, which is important because clients should not choose another customer's ID.
  • Amounts are stored in minor currency units. For INR, 149700 means ₹1,497.00.
